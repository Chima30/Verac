# Post-Quantum AI Agents: compliance matrix and gap analysis

Audit date: 2026-11-16, on branch `feat/agent-workflow`.

This file maps each requirement of the Build Before Q-Day "Post-Quantum AI Agents" category to code, enforcement layer, on-chain configuration, test procedure and real evidence. A requirement is marked **Verified on-chain** only when a transaction or a chain read-back proves it. A UI badge is never evidence.

Status words used below:

- **Verified on-chain**: a confirmed transaction, or a recorded revert, on Diana testnet.
- **Verified by local test**: an automated test in this repository that passes.
- **Configured, not yet proven**: the chain accepted the configuration, but the negative case has not been demonstrated.
- **Prepared, not run**: a script exists, but running it needs testnet signing that the owner has not yet approved.
- **Not yet verified**.

## Gap analysis against the full brief

| Area | What existed at audit time | Gap | Plan in this branch |
|---|---|---|---|
| Multi-agent workflow | `Coordinator` with a single-agent keyword router, tool allow-list and `MessageBus`. No agent ever worked on real organisation data together with another. | No orchestration across agents and no persisted workflow. | Add an invoice-review workflow: Invoice, Milestone, Security, Treasury, Policy and Payment agents over a snapshot of the organisation's records, exchanging signed messages, with every step persisted. |
| Invoice records | The `invoices` and `vendors` tables existed with RLS, but no page wrote to them. Bills & Invoices was a stateless checker. | There were no real invoices to review. | Migration 0016: invoice → milestone link, `record_invoice` RPC, vendor form, demo-scenario seeding labelled as synthetic data. |
| Durable execution | None. AI routes ran inside one HTTP request. | Workflows would not survive a refresh or a crashed worker. | Workflow state in `agent_tasks` with step results, a lease (`lease_until`), attempts and an idempotency key. Each request advances one step, and the page or a cron tick resumes stalled runs. |
| Payment link | `proposeLivePayment` (chain-checked, hash-bound), `decide_live_payment` (step-up password, requester ≠ approver), `executeLiveOperation` (claim, window, relay approval, execute, receipt and event check). | No link from an AI finding to a payment request, and no decision receipt. | The PaymentAgent prepares eligible invoices through `proposeLivePayment`, unchanged, with the invoice and workflow ids recorded in the evaluation. Decision receipts are built from the stored records. |
| Gemini | Structured outputs with Zod, rate and daily limits, retries, quota pause, untrusted-data wrapping, secret scan. | Not used for instruction parsing or report wording. | Optional parse-to-allow-listed-intent and report wording, with deterministic fallbacks. Gemini never decides eligibility. |
| Custody | The agent and approver keys are both in server env vars. | **A compromised server could relay an approval and execute without a human.** The database refuses a requester self-approving and requires the password step-up, but those checks live on the same server. | Documented in SECURITY.md as the main remaining risk. Not weakened. Real fix: the approver signs from their own wallet (QoreX). |
| Foundry | Contract tests exist (`contracts/test`). | `forge` is not installed on this machine, so they were not run in this audit. | Documented. Run `forge test` in CI or after installing Foundry. |
| Browser E2E | Playwright layout suite (desktop, tablet, mobile; no auth). | No signed-in workflow test: no test Supabase project is available here. | Added mocked-service workflow tests in Vitest (`engine.test.ts`). A signed-in Playwright flow needs an isolated Supabase project with test users and is **not written yet**; see DEMO_CHECKLIST.md. |
